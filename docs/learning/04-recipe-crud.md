# Этап 2, шаг 3: CRUD рецептов

Код: `recipe/RecipeController`, `RecipeService`, `RecipeDtos`; тест `RecipeApiTest`.

## Эндпоинты

| Метод | Путь | Ответ | Что делает |
|---|---|---|---|
| POST | `/api/recipes` | 201 + `Location` | Создать рецепт |
| GET | `/api/recipes/{id}?servings=2` | 200 | Рецепт; с `servings` у ингредиентов есть пересчитанное `scaled` |
| PUT | `/api/recipes/{id}` | 200 | Заменить рецепт целиком, нужен `version` |
| DELETE | `/api/recipes/{id}` | 204 | Мягкое удаление |
| POST | `/api/recipes/{id}/restore` | 200 | Вернуть из корзины |
| PATCH | `/api/recipes/{id}/favorite` | 200 | `{"favorite": true}` |

Чужой рецепт на любой операции → 404. Без токена → 401. Неверные поля → 400 со списком ошибок. Устаревшая версия → 409.

## Новые аннотации

**`@PathVariable`** — взять значение из пути: в `/api/recipes/{id}` для `/api/recipes/42` параметр `id` будет `42`. Spring сам переведёт строку в `Long`, а если там `abc`, ответит 400.

**`@RequestParam(required = false)`** — параметр из строки запроса `?servings=2`. `required = false` — можно не передавать, тогда придёт `null`.

**`@PutMapping`, `@DeleteMapping`, `@PatchMapping`** — как `@PostMapping`, только для других HTTP-методов. Смысл по REST:
- `PUT` — заменить ресурс целиком (форма редактирования отправляет всё);
- `PATCH` — поменять кусочек (только избранное);
- `DELETE` — удалить.

**`@ResponseStatus(HttpStatus.NO_CONTENT)`** — при удалении вернуть 204 «успешно, тела нет».

**`ResponseEntity`** — когда нужно управлять не только телом, но и статусом и заголовками. В `create` возвращаем 201 и заголовок `Location: /api/recipes/42` — адрес нового ресурса, так принято в REST.

**Валидация внутри списка**: `List<@NotBlank @Size(max = 500) String> ingredients` — аннотации на типе элемента проверяют каждую строку списка, а `@Size(max = 100)` на самом списке ограничивает количество.

**`@Pattern(regexp = "https?://.*")`** — строка должна подходить под регулярное выражение. Так ссылка на источник не может быть `javascript:...`, это защита от XSS на фронтенде.

**`@OptimisticLock(excluded = true)`** (Hibernate) на поле `favorite` — изменение этого поля не увеличивает `version`. Иначе лайк на телефоне ломал бы сохранение редактирования на ноутбуке с ошибкой 409, а это два независимых действия.

## Устройство сервиса

**Владелец проверяется в запросе.** `findOwnedWithDetails(recipeId, userId)` ищет рецепт сразу с условием `owner.id = :userId`. Отдельно сравнивать владельца не нужно, а чужой рецепт неотличим от несуществующего. Если бы мы отвечали 403, злоумышленник мог бы перебирать id и узнавать, какие рецепты существуют.

**`users.getReferenceById(userId)`** — не делает `SELECT` пользователя, а возвращает заглушку с одним id. Для внешнего ключа `user_id` этого достаточно, лишний запрос не нужен.

**Ингредиенты приходят строками.** Клиент шлёт `"500 г фарша"`, сервер сам разбирает через `IngredientParser` и сохраняет и исходную строку, и разобранные поля. Фронтенду не нужно знать правила разбора.

**Теги ищутся без учёта регистра.** `"Italian"`, `"italian "` и `"ITALIAN"` — один тег. Существующие переиспользуются, новые создаются.

**Версия проверяется два раза.**
1. Явно: если `request.version` не равна текущей, сразу 409. Это ловит случай «открыла форму вчера, сохранила сегодня».
2. Через `@Version`: если два запроса пришли одновременно и оба прошли первую проверку, Hibernate увидит, что `UPDATE ... WHERE version = 0` не обновил строку, бросит `ObjectOptimisticLockingFailureException`, и `ApiExceptionHandler` превратит её в 409.

**`recipes.flush()` в `update`.** Обычно Hibernate отправляет `UPDATE` в конце транзакции. Здесь мы вызываем его раньше, чтобы в ответе уже была новая `version`, иначе клиент получил бы старую и следующее сохранение упало бы с 409.

**`Clock` как бин** (`TimeConfig`). Вместо `OffsetDateTime.now()` пишем `OffsetDateTime.now(clock)`. В тестах можно подставить `Clock.fixed(...)` и проверять время точно, например «удалено 31 день назад → чистится».

## Тест RecipeApiTest
`@SpringBootTest` + `MockMvc` — полный путь запроса: security, валидация, контроллер, сервис, база. Каждый тест регистрирует нового пользователя со случайным email, поэтому тесты не мешают друг другу.

Проверяется:
1. Создание: 201, `Location`, разобранные ингредиенты, склеенные дубли тегов.
2. Пересчёт: 500 г на 4 порции → 250 г на 2; 1½ ч. л. → ¾; 2 яйца → 1; «по вкусу» не пересчитывается.
3. Редактирование: всё заменилось, версия 0 → 1; повторная отправка с версией 0 → 409.
4. Избранное не меняет версию.
5. Удаление и восстановление.
6. Чужой рецепт → 404 на GET, PUT, DELETE и restore.
7. Пустое название, 0 порций и `ftp://` ссылка → 400 с тремя ошибками полей.
8. Без токена → 401.
